# Agent、正文版本与渲染改进审计

更新时间：2026-08-23

## 1. 结论

当前实现已经具备可用的 Agent 写作主链路、SSE 事件恢复、会话内任务互斥、正文版本号和不可变版本快照。其可靠边界目前是：**单个后端进程、单个浏览器标签页、以 Agent 完成作为正文提交入口**。

进入多人、多标签页或多进程部署前，仍需优先解决以下四类问题：

1. 正文修改任务的草稿与已提交正文没有在恢复界面严格分离。
2. 普通保存未携带 `base_version`，多标签页编辑可能后写覆盖先写。
3. 选区修改经过全文校验后，修订节点可能改动选区之外的内容。
4. “同一会话一个活动任务”和事件序号互斥目前只在单进程内可靠。

编码方面没有发现网页或 DOCX 主链路把中文转换成乱码。实际页面为 UTF-8，正文中未发现 `U+FFFD` 替换字符；中文 Markdown 经默认模板导出 DOCX 后能够完整回读，中文字体声明也存在。仍需处理非 UTF-8 上传文件、显式中文字体回退、异常模板及移动端遮挡问题。

## 2. 已具备的保障

### 2.1 Agent 与正文版本

- 前端在一个标签页内使用会话任务表阻止同一会话重复启动任务。
- 后端创建任务时检查同一会话是否已有 `queued` 或 `running` 任务。
- 不同会话可并行运行，默认总并发数为 3。
- Agent 创建时记录 `base_version`；完成时再次比较当前 `article_version`，版本不同则不覆盖正文。
- Agent 成功提交和用户保存都会增加正文版本，并写入 `DocumentRevision`。
- `DocumentRevision(session_id, version)` 和 `AgentEvent(run_id, seq)` 已有唯一约束。
- SQLite 已启用外键、WAL 和 30 秒 busy timeout。
- 取消、失败、重启中断和重试已有持久状态；SSE 事件也可按游标重放。

### 2.2 编辑器协作

- 新建正文时，`content.delta` 以约 180 ms 的批次进入编辑器，避免逐 token 重渲染。
- 修改已有正文时，运行期间保留旧正文并设为只读；成功后以后端已提交结果一次性替换。
- Agent 完成提交前检查正文版本，失败、取消或版本冲突时不会在后端覆盖已提交正文。
- 编辑器保留目录、内容审查、保存、选区修改和 Markdown/DOCX 导出。

### 2.3 中文与导出验证

- 页面声明 `lang="zh-CN"`，浏览器识别字符集为 UTF-8。
- 当前页面可见正文中 `U+FFFD` 数量为 0，连续问号乱码数量为 0，控制台无错误或警告。
- 中文 Markdown → Pandoc → 默认 DOCX 模板的内存测试通过：Word XML 含原始中文，`python-docx` 回读文本与输入一致。
- 默认 DOCX 模板中存在仿宋等中文字体声明。
- 前端构建和静态检查通过；前端 8 个单元测试、后端 46 个测试通过。

## 3. P0：提交下一轮功能前必须处理

### P0-1 恢复页面会显示未提交的修改草稿

证据：`frontend/src/App.jsx:307-313` 对 `queued/running/failed/interrupted` 的最新任务统一优先使用 `article_snapshot`，没有区分新建正文和修改已有正文。

影响：已有正文执行全文修改或选区修改时，如果刷新页面、切换会话后再返回，界面可能显示运行中或失败的草稿；用户会误以为草稿已经保存。后端已提交正文虽然仍安全，但界面语义错误，后续保存还可能把失败草稿真正提交。

建议：

- 明确区分 `committed_article`、`working_draft` 和 `stream_preview`。
- 只有 `base_version == 0` 的新建任务可以在恢复时用草稿替代空正文。
- `revise_document`、`revise_selection` 的草稿只能显示在运行详情中；编辑器始终显示已提交版本，成功事件到达后再原子切换。
- 失败或取消后提供“查看失败草稿”，但不得默认写入编辑器。

### P0-2 全文修改可能忽略未保存的编辑器内容

证据：`frontend/src/App.jsx:721-725` 使用 `currentSessionOutput` 构造 `base_article`；当前编辑内容另存在 `editorRealtimeContent`。普通编辑后若尚未完成保存，两者可能不一致。

影响：用户刚手工修改的内容可能未进入 Agent 输入，Agent 完成后又覆盖这些修改。

建议：启动全文修改前从编辑器实例取得最新 Markdown；先以带版本号的保存完成一次提交，再以返回的新版本创建 Agent 任务。保存失败或版本冲突时不得启动模型调用。

### P0-3 选区修改的二次修订可能越界

证据：初稿阶段通过 `backend/app/agent/graph.py:194-200` 精确替换唯一选区；但 `graph.py:640-710` 随后对全文校验，并要求修订节点输出完整全文，没有再次限制选区边界。

影响：初次替换严格局限于选区，校验触发的第一或第二次修订却可能改变全文其他段落，违背“局部修改”承诺。

建议：

- 选区任务的校验对象以“替换文本 + 只读上下文”为主。
- 修订节点只返回新的 replacement，不返回全文。
- 每次修订后重新执行 `_apply_selection`。
- 提交前做确定性边界检查：选区前后正文必须与基线逐字一致。

### P0-4 多进程部署没有真正的会话任务锁和写入所有权

证据：

- `backend/app/agent/manager.py:153-173` 是“查询活动任务后再插入”，数据库没有活动任务的部分唯一索引。
- 并发信号量、任务表、取消集合和事件锁均是进程内对象（`manager.py:103-108`）。
- 每个进程启动时都会把数据库内所有活动任务标成 interrupted（`manager.py:136-144`）。
- 事件序号通过进程内锁后执行“读取并加一”（`manager.py:462-490`）。

影响：两个后端 worker 可能为同一会话同时创建任务、重复事件序号、无法真正取消另一个 worker 中的任务；新 worker 启动还可能中断旧 worker 正在执行的任务。

建议分两阶段：

1. 短期在部署文档中明确只允许一个 Uvicorn worker，并在启动时检测配置，避免误部署。
2. 扩展为多 worker 前，增加数据库活动任务唯一约束、`worker_id/lease_expires_at` 所有权租约、条件状态更新和可跨进程的取消标记；事件序号改为数据库原子分配。

## 4. P1：下一轮稳定性改造

### P1-1 所有正文保存必须使用乐观锁

后端 `SaveArticleIn` 已支持 `base_version`，但前端 `writeApi.saveArticle(...)` 的现有调用没有传入版本。多标签页普通保存因此仍是最后写入者覆盖前一个写入者。

需要统一：

- 会话加载后，前端保存 `article_version`。
- 手工保存、导出前保存、选区修改前保存、全文修改前保存都必须提交 `base_version`。
- 后端用单条条件更新实现 compare-and-swap，而不是“先读取、后比较、再更新”。
- 成功响应返回新版本；409 时展示可理解的冲突提示，并提供重新加载，不自动覆盖。
- 活动 Agent 期间，其他标签页仍可保存，但应提示这会使运行结果产生版本冲突；也可选择阻止并节省模型调用成本。

### P1-2 保存错误不能被吞掉

`frontend/src/App.jsx` 的文章保存处理会捕获异常并只写控制台，而编辑器上层因此可能认为保存已完成。需要让异常继续向上抛出，并让保存按钮、导出前保存和 Agent 启动显示一致的失败状态。

### P1-3 使用数据库原子提交正文版本

Agent 完成时已有版本检查，但当前仍是 ORM 的读—改—写事务。建议使用：

```text
UPDATE sessions
SET article_content = :article, article_version = article_version + 1
WHERE session_id = :session_id AND article_version = :base_version
```

受影响行数为 0 时即为版本冲突。随后在同一事务写入 `DocumentRevision` 和 Agent 完成状态。

### P1-4 SSE 恢复需要明确“快照 + 增量”的基线

`frontend/src/App.jsx:165` 在 `after > 0` 时把当前 `article_snapshot` 作为初始正文，随后再追加游标之后的 delta。若快照已经包含这些增量，初次生成的恢复画面可能重复内容。

建议让服务端返回 `snapshot_event_seq`，前端只重放该序号之后的事件；或者恢复时始终从事件 0 重建预览。增加断线发生在 append、replace 和 completed 前后的组合测试。

### P1-5 编辑器状态源应合并

目前同时维护 `currentSessionOutput`、`editorRealtimeContent` 和 MDXEditor 内部状态。建议建立单一的正文状态模型：

```text
committed { markdown, version }
working   { markdown, dirty }
agent     { runId, baseVersion, preview, status }
```

由状态机决定编辑器显示、只读、保存和覆盖，避免多个 state 之间依靠 effect 间接同步。

### P1-6 恢复版本能力尚未交付到用户界面

数据库已经保存 `DocumentRevision`，但没有版本列表、查看和恢复入口；Agent 覆盖后编辑器还会重置撤销历史。建议提供轻量的“历史版本”抽屉和恢复接口。恢复本身也必须基于当前版本做乐观锁，并生成新的版本，不能改写旧快照。

### P1-7 移动端布局实际不可用

在 390×844 的实际浏览器检查中：

- 会话栏固定占用约 200 px 高度。
- 对话面板始终以约 405 px 高的 fixed 面板覆盖正文。
- 正文编辑器与对话面板重叠约 405 px。
- 目录存在时，编辑器工具栏可见宽度只有约 93 px，虽然工具栏可横向滚动，但正文操作空间过小。

建议移动端默认只显示正文；会话列表和对话分别改为可关闭抽屉，抽屉关闭时不得继续遮挡正文。目录改为按钮触发的临时面板。

### P1-8 模板路径和 DOCX 有效性需要校验

问题：

- 导出接口直接把 `reference_doc` 拼到 `format` 路径（`backend/app/routers/content.py:285-299`），未验证最终解析路径仍在模板目录内，也未确认它来自模板表。
- 模板上传只检查 `.docx` 扩展名，文件名未统一使用 basename/UUID，也不验证 ZIP/Word 结构。
- Pandoc 超时或异常时临时文件可能残留；Pandoc 的 stderr 还会原样返回给前端。

建议：导出只接收 `template_id`；从数据库解析文件名；使用 `Path.resolve()` 校验目录边界；模板保存名使用 UUID；上传时限制大小并验证 `[Content_Types].xml`、`word/styles.xml`；所有临时文件使用 `finally` 清理；对前端只返回稳定错误码。

### P1-9 非 UTF-8 文本上传会失败或残留 BOM

`backend/app/routers/content.py:138-141` 和 `backend/app/services/document_processor.py:73-78` 只按严格 UTF-8 读取 `.md/.txt`。

建议读取顺序为：UTF-8 BOM → UTF-8 → 可配置的 GB18030；无法可靠识别时返回“请另存为 UTF-8”的明确提示。不要静默用 replacement 模式吞掉错误字节。为 UTF-8、UTF-8 BOM、GB18030、混合非法字节分别加测试。

### P1-10 Skill 与文种在修改任务中没有被保留

全文和选区修改都硬编码 `document_type: 'general'`，并默认关闭 KnG（`frontend/src/App.jsx:710-753`）。因此修改阶段实际使用通用公文 Skill，而不是原起草时的通知、制度或讲话稿 Skill；会话也没有持久化原文文种和已选 Skill。

建议在会话/文档元数据中持久化 `document_type` 和 primary skill。修改任务沿用原文 Skill；只有用户明确改变文种时才重新选择。是否检索应由修改意图和用户开关决定，而不是永久关闭。

### P1-11 Checkpoint 和事件缺少保留策略

本次本地样本只有 1 个 Agent run，checkpoint SQLite 已约 7.6 MB；主库 WAL 曾约 4.2 MB。一个运行写入了 126 条 `content.delta`。完整状态、原始检索和草稿在多个检查点重复保存，长期运行会快速膨胀。

建议：

- 完成后保留必要安全检查点，定期清理过期中间检查点。
- 对事件设置保留期限或归档规则；完成任务可合并高频 delta。
- 降低草稿数据库更新频率，避免每 180 ms 一次写入。
- 监控数据库、WAL、checkpoint 大小和清理失败。

## 5. P2：质量与可维护性改进

### P2-1 显式添加中文字体回退

网页当前字体栈主要是系统 UI 和西文字体。在常见 Windows 浏览器中会自动回退并正常显示，但精简 Linux 桌面或容器化浏览器可能出现方框字。

建议正文和界面分别加入：

```css
font-family: "Noto Sans CJK SC", "Source Han Sans SC", "Microsoft YaHei",
  "PingFang SC", system-ui, sans-serif;
```

这解决的是“缺字形”，不是字符编码问题。公文正式字体仍以 DOCX 模板为准，网页不模拟 Word 分页。

### P2-2 建立 Markdown 兼容范围

MDXEditor 当前支持标题、列表、引用、表格和链接等常用格式，但任意 HTML、复杂 MDX、自定义块和异常实体未纳入稳定契约。需要定义允许的 Markdown 子集，并用中文公文语料测试：公文编号、全角标点、表格、长标题、特殊字符、链接、连续空行、CRLF 和 HTML entity 的加载—编辑—保存—导出往返一致性。

### P2-3 来源需要稳定身份和规范化去重

相同材料可能以编号标题、语料路径标题等形式重复出现。当前只按字符串去重会造成来源数量和展示不稳定。建议生成内部 `source_id`，保留原始标题作为显示字段，并按规范化路径/标题合并。正文事实仍必须绑定过滤后的证据，标题不能单独证明事实。

### P2-4 模型审阅和证据一致性仍需真实语料评测

现有单元测试证明流程和边界能运行，但不能证明模型在所有中文公文中都能正确判断“直接相关/部分相关/无关”。应建立固定的网络安全、保密、教学、科研、人事等混淆语料集，测量无关证据进入正文率、无依据事实率和重要用户事项遗漏率。

### P2-5 后端静态资源挂载存在构建窗口竞态

`backend/app/main.py:83-85` 只判断 `frontend/dist` 是否存在，随后直接挂载 `dist/assets`。前端构建重建目录的短暂窗口内，后端导入会失败。本轮并行运行构建和测试时已复现；构建结束后后端 46 个测试全部通过。

建议同时检查 `dist/index.html` 和 `dist/assets`；生产环境使用不可变构建目录并原子切换，不在运行目录原地清空重建。

### P2-6 数据库相对路径依赖启动目录

默认 `sqlite:///./writing_assistant.db` 相对于进程工作目录。不同启动方式可能创建不同数据库。建议把默认路径解析到明确的 `backend/data/`，日志启动时打印脱敏后的绝对数据库位置，并在部署中显式设置 `DATABASE_URL`。

### P2-7 清理弃用和重复定义

- `payload.dict()` 已触发 Pydantic 2 弃用警告，应改为 `model_dump()`。
- `backend/app/schemas.py` 中 `TemplateOut` 重复定义多次。
- 旧 proposal 数据列可按既定兼容策略暂留，但应标注废弃版本和最终清理迁移。
- Vite 主包约 911 KB，构建已有大 chunk 警告；可按编辑器/Agent 面板拆包，改善首屏加载。

### P2-8 收敛对外错误与跨域配置

部分旧接口把异常文本或 Pandoc stderr 返回给前端；生产 CORS 仍为全开放。应统一公开错误码和用户提示，详细异常只入服务端日志；部署时按实际前端域名配置 CORS。

## 6. 目标并发与版本模型

### 6.1 当前能力矩阵

| 场景 | 当前结果 | 结论 |
| --- | --- | --- |
| 同一标签页、同一会话重复启动 Agent | 前端阻止 | 可用 |
| 单进程后端、同一会话重复创建 Agent | 后端查询阻止 | 基本可用 |
| 单进程后端、不同会话并发 | 默认最多 3 个 | 可用 |
| Agent 运行时正文被另一次保存更新 | 完成时版本冲突，不覆盖 | 可用但浪费模型成本 |
| 两个标签页同时普通保存 | 未传 `base_version`，后写覆盖 | 不安全 |
| 刷新后恢复已有正文修改任务 | 可能显示未提交草稿 | 不安全 |
| 多个后端 worker | 锁、取消、启动恢复均为进程内 | 不支持 |

### 6.2 目标规则

1. `article_version` 只代表已提交正文，不代表 Agent 草稿。
2. 所有写入都必须声明所基于的版本。
3. 同一会话同一时刻只能有一个活动 Agent，由数据库约束而非内存约定保证。
4. Agent 的 `base_version` 在整个运行中不变；重试时创建新的 attempt 并明确更新基线。
5. 提交正文使用数据库 compare-and-swap；失败时运行结果保留为未应用草稿。
6. 任意历史恢复都创建新版本，历史快照不可变。
7. SSE 游标只控制事件传输，不能替代正文版本。
8. 草稿版本、已提交版本和编辑器 dirty 状态必须在 API 和界面中分别表达。

## 7. 建议实施顺序

### 阶段 A：数据正确性

1. 修复修改任务恢复时显示未提交草稿的问题。
2. 合并正文状态源，Agent 启动前保存最新编辑器内容。
3. 所有保存传递 `base_version`，后端改为原子 compare-and-swap。
4. 修复选区二次修订越界。
5. 明确单 worker 部署限制，并增加启动保护。

### 阶段 B：恢复与多窗口

1. 定义 SSE 快照序号，补全断线重连测试。
2. 增加版本历史查看和恢复。
3. 为多 worker 增加数据库活动任务锁、租约和跨进程取消。
4. 增加 checkpoint/event 保留与监控。

### 阶段 C：渲染与文件

1. 修复移动端抽屉和目录布局。
2. 增加中文字体回退和 Markdown 兼容语料测试。
3. 支持 UTF-8 BOM/GB18030 的明确解析策略。
4. 收紧模板 ID、路径、结构、大小和临时文件清理。
5. 增加实际 DOCX 生成、解包、中文回读和字体样式检查。

### 阶段 D：质量与运维

1. 建立 KnG 相关性与事实约束评测集。
2. 收敛错误响应、CORS 和数据库绝对路径。
3. 清理弃用代码、重复 schema 和前端大包。

## 8. 必须新增的验收测试

### 并发和版本

- 两个标签页基于同一版本保存：只能一个成功，另一个收到 409，正文不丢失。
- 同一会话两个并发 Agent 创建请求：数据库层只能存在一个活动任务。
- 三个不同会话并行运行：均能完成，事件和正文版本互不串线。
- Agent 运行中用户保存新版本：Agent 完成时保留用户版本，并把 Agent 结果标为未应用。
- 失败/取消/版本冲突后刷新：编辑器仍显示最后提交正文。
- 两个 worker 同时启动、取消和重试：不会互相标记 interrupted，不产生重复事件序号。

### 修改边界

- 全文修改前存在未保存编辑：Agent 基线必须包含该编辑。
- 选区修改触发两次修订：选区前后内容逐字不变。
- 选中文本出现多次或基线已变化：拒绝提交并保留原文。
- Agent 覆盖后可从版本历史恢复，恢复生成新版本。

### SSE 和编辑器

- 在 append、replace、completed 前分别断线重连，正文不重复、不缺失。
- 重复事件 ID 被去重；乱序或缺口会重新拉取快照。
- 新建正文可流式显示；已有正文修改不把增量写进正式编辑器。
- 运行、失败、取消、冲突的只读状态和提示符合预期。

### 中文和渲染

- UTF-8、UTF-8 BOM、GB18030 中文 TXT/MD 上传结果正确。
- 标题、全角标点、生僻字、表格和长段落经过编辑器往返后不改变字符。
- 页面 DOM 不含 `U+FFFD`，缺少首选字体时仍有指定中文字体回退。
- 390×844 下正文为主视图，对话和会话抽屉可关闭且不遮挡正文。
- DOCX 导出后解包检查中文 XML，并用 `python-docx` 回读正文；默认模板字体和段落样式符合预期。
- 损坏模板、伪 DOCX、超大模板和越界模板参数均被安全拒绝。
